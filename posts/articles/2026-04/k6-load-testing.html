Building a k6 Load Testing Project (TypeScript + InfluxDB + Grafana)

Apr 8, 2026 #k6 #LoadTesting #TypeScript #Grafana #InfluxDB #Docker 6 min

Intro

I wanted a load testing project that’s easy to run locally, easy to extend to new targets, and produces dashboards that the whole team can read. That became k6-load: a TypeScript k6 repo bundled with esbuild, with two kinds of tests (HTTP + browser), and a simple observability stack (InfluxDB + Grafana) that you can keep running while you fire off short-lived k6 runs.

The two key decisions were:

  • Keep load generation ephemeral (k6 runs in one-off containers).
  • Keep observability persistent (InfluxDB + Grafana runs as a long-lived Docker Compose stack).

Project layout and naming

The repo is organized around targets. Each target has its own scripts, env template, and (optionally) browser scenarios:

  • src/targets/slicedice/ — API + browser test flows against my Slice Dice app.
  • src/targets/starwars/ — a public HTTP example using SWAPI (good for verifying the stack quickly).
  • dist/*.js — esbuild output; these are the files you actually execute with k6 run.
  • grafana/ — provisioning for datasource + dashboards.

I also standardized a few conventions so “new target” doesn’t turn into “new snowflake”:

  • Bundle names: slicedice, starwars (folder + dist output).
  • Buckets: one per target, like k6_slicedice, k6_starwars.
  • Run labels: LOAD_TEST_TYPE becomes a k6 tag so Grafana can slice runs by intent (simulate_traffic, database_optimization, etc).

Why TypeScript for k6

k6 runs JavaScript, but for any non-trivial suite I like TypeScript’s types, refactors, and shared libraries. The repo builds with esbuild into dist/ so the runtime stays simple: 

              
                npm install
                npm run build
                k6 run dist/starwars.js

Most runs happen in a container image that already includes k6 and the Influx output plugin, so you don’t need to install k6 locally. If you do install k6 locally, it’s mainly for a nicer debugging loop (especially for browser scenarios).

Quick start

The workflow is: start the long-lived observability stack once, then run short-lived k6 jobs against whichever target you want. 

              
                cp .env.example .env
                docker compose -f docker-compose.observability.yml up -d

Then run a quick test to confirm everything is wired correctly: 

              
                docker compose -f docker-compose.k6.yml build
                docker compose -f docker-compose.k6.yml --env-file .env --env-file .env.example.starwars run --rm k6-starwars

InfluxDB + Grafana via Docker Compose

The observability stack is started once and kept running: 

              
                cp .env.example .env
                docker compose -f docker-compose.observability.yml up -d

After that, each test run only needs to ship metrics to InfluxDB. Grafana is pre-provisioned with a datasource and a starter dashboard (k6 overview) that can filter by bucket, scenario, and test type.

Two common gotchas

  • Influx “unauthorized”: InfluxDB 2 needs an API token (not the UI password). If the token in your .env doesn’t match what Influx was initialized with, metrics will fail to write. When iterating locally, a clean reset is often simplest: 
                      
                    docker compose -f docker-compose.observability.yml down -v
                    docker compose -f docker-compose.observability.yml up -d
  • k6 can’t reach localhost: inside Docker, localhost is the runner container. To hit a service on your host, use http://host.docker.internal:<port> (or use a compose service name if the target is on the same network).

Make load tests “real” (user pools)

The fastest way to get misleading results is to load test with one account. You’ll over-reuse cached data and accidentally benchmark the “best case” path. For app-like targets, k6-load uses a pool of users (YAML) and assigns one user per VU so sessions and permissions vary across the run.

For Slice Dice, there’s a helper to seed users: 

              
                ./scripts/slicedice/seed-users.sh

API target: authentication + a YAML user pool

For app-like targets, I wanted “many users” without copying credentials into scripts. The Slice Dice target reads a YAML array of users (mounted into the k6 container) and assigns a user per VU.

At runtime you mostly care about:

  • BASE_URL — where the API lives.
  • USERS_FILE — path to a YAML user list (mounted into the container).

One subtle point: inside Docker, http://localhost points at the k6 container, not your laptop. If you’re load testing an API running on the host, use http://host.docker.internal:<port> (or a compose service name if it’s on the same docker network).

Browser scenarios: useful grouping without relying on group()

With k6 browser, group() is not reliable with async actions, which makes it hard to build “page-level” dashboards by group name alone.

The approach in k6-load is to record an async-safe flow metric (a Trend) and tag it with a flow label (page-object style steps like login, browse menu, checkout). The Grafana dashboard then filters and compares those tagged flow durations alongside the usual request metrics.

Grafana Dashboard

The repo ships a starter “k6 overview” dashboard with variables for bucket, client (HTTP / browser), scenario, page group, and test type. The variable values are derived from the metrics present in InfluxDB for the selected time range, so you can quickly narrow down to the exact run you care about.

Reloading dashboards while iterating

When editing grafana/dashboards/*.json, I prefer a quick provisioning reload instead of restarting the whole stack: 

              
                ./scripts/reload-grafana-dashboards.sh

Wrap-up

The end result is a repo that makes iteration cheap: add a target, bundle to dist/, run k6 in a disposable container, and always have the same dashboards waiting in Grafana. If you want to see the full setup (compose files, scripts, and the starter dashboard), the source is here: jsnwu/k6-load.
