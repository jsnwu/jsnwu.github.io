Web app performance optimization: caching, backend, CDN, search, load balancers

Apr 14, 2026 #Performance #Caching #Backend #CDN #Elasticsearch #LoadBalancer 8 min

Intro

When a web app is “slow”, it’s usually not one thing. It’s a stack of small delays: extra network round trips, heavy assets, inefficient queries, repeated work in the backend, and hot endpoints that don’t scale under load.

This post is a practical checklist from five angles that tend to move the needle the most: caching, backend performance, CDN, Elasticsearch, and load balancers.

1) Implement effective caching strategies

Caching is “store work once, reuse it later”. The key is to cache the right thing at the right layer, with a clear invalidation story.

Browser / HTTP caching

  • Static assets (CSS/JS/images/fonts): cache aggressively with long max-age and versioned filenames (or querystrings) so you can invalidate by deploy.
  • API GET responses: use ETag (or Last-Modified) and conditional requests so repeat navigations become cheap.
  • stale-while-revalidate: serve a slightly stale response immediately while revalidating in the background for a smoother UX. 

              Cache-Control: public, max-age=3600, stale-while-revalidate=600

Backend / server-side caching

  • In-memory: fastest, simplest, but per-instance and limited by RAM (good for config, small lookups, hot computed values).
  • Distributed (Redis/Memcached): shared across instances; better for scaled services and consistent hit rates.
  • Cache the “expensive shape”: cache rendered fragments, aggregated API payloads, or “materialized” results rather than raw rows.

Cache invalidation (the part that bites)

  • TTL: easy; accept short staleness windows.
  • Write-through: update cache and DB together for hot writes.
  • Versioned keys: prefix cache keys by schema or rollout version (e.g. v2:product:123).
  • Explicit invalidation: publish “entity updated” events to clear/refresh dependent keys.

2) Improve backend performance

Backends feel slow because of latency (time spent waiting) or throughput limits (time spent working). The common wins:

Measure first

  • Trace requests: where is time spent—DB, cache, external API, serialization?
  • Log slow queries: collect query text + params + timing.
  • Track p95/p99: averages hide tail latency.

Database: fewer round trips, better plans

  • Indexes that match access patterns (especially composite indexes for multi-column filters).
  • Kill N+1s: batch, join, or prefetch.
  • Pagination: prefer keyset (cursor) pagination for large tables over large offsets.
  • Connection pooling: keep pools sized for DB limits; avoid connection churn under bursty traffic.

API shape and concurrency

  • Batch calls: fewer requests often beats smaller payloads.
  • Async work: move slow side effects to queues and return quickly.
  • Compression: use Brotli/Gzip where it helps (HTML/JS/CSS; be careful with already-compressed binaries).

3) CDN: reduce latency and protect the origin

A CDN is not just for images. It’s a latency reducer, bandwidth saver, and an origin shield.

  • Cache static assets close to users; remove repeated origin downloads.
  • Use edge caching for semi-dynamic responses (careful with auth/cookies).
  • Origin shielding: protect your app from thundering herds on cold caches or traffic spikes.
  • Modern protocols: enable HTTP/2 and HTTP/3 where possible; multiplexing reduces connection overhead.

4) Elasticsearch: fast search without melting your DB

If your app has “search” that reads like analytics (multi-field filtering, partial text, relevance), pushing it onto the OLTP database usually backfires. Elasticsearch is great when you treat it as a derived index.

Patterns that work well

  • Write model ≠ read model: keep DB normalized; index a denormalized document for search.
  • Async indexing: use an outbox/queue so search indexing doesn’t block request latency.
  • Filter-first queries: use keyword fields for filters, full-text fields for relevance, and avoid expensive wildcard patterns on large datasets.
  • Cache results carefully: cache common queries (or popular facets) with short TTLs to absorb spikes.

Scaling tips

  • Keep mappings stable: frequent mapping changes cause reindex pain.
  • Shards are not free: start small; scale shards with data size and query concurrency.
  • Protect with rate limits: search endpoints are easy to abuse.

5) Load balancers: throughput, availability, and tail latency

A load balancer should make your app more reliable. Misconfiguration can do the opposite—especially under retries and connection churn.

  • Health checks: make them representative (cheap, but real). Ensure instances drain properly on deploy.
  • Sticky sessions: avoid unless required. Prefer stateless servers + shared session store.
  • Timeouts: set sensible client, LB, and server timeouts; avoid “infinite waits” that tie up resources.
  • Keep-alive: reuse connections; reduce TLS handshake overhead.
  • Rate limiting: protect hot endpoints and upstream dependencies.

Measuring web performance (manual + CI)

Optimization is easy to do wrong if you don’t measure. For quick manual assessment, I like a small checklist that you can run in a few minutes and repeat consistently.

Manual quick assessment

  • Lighthouse (Chrome DevTools): run it in an Incognito window (no extensions, cold-ish cache) and focus on a few repeatable numbers: LCP, CLS, total blocking time, and the overall score.
  • Network tab: check total request count, the largest assets, and whether static assets are cacheable (Cache-Control, ETag).
  • Fast reality check: throttle CPU/network to catch obvious “works on my machine” regressions.

Automate it daily with Playwright in CI/CD

For ongoing monitoring, you can run performance checks on a schedule (daily) or on key branches. A common pattern is: use Playwright to navigate to a set of URLs, then run Lighthouse against the same pages and publish a small report.

  • Pick a stable environment: run against staging or a pinned build to reduce noise.
  • Control variables: consistent device profile, cache mode, and throttling settings.
  • Track trends: store results over time; alert on regressions (e.g. LCP p95 > threshold).

Wrap-up

The fastest performance wins tend to come from eliminating repeated work: cache what’s expensive, reduce unnecessary network calls, and make “hot paths” predictable under load. Start with measurement, pick the highest-leverage bottleneck, and iterate.
